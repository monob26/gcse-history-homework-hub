## Local improvements prepared

The teacher page now preserves Auth `Retry-After` through a fetch wrapper without reading/logging
payloads. It handles HTTP 429 and the documented request/email rate error codes, displays a wait,
and prevents simultaneous or repeated form submissions during that action's pause. Numeric and
HTTP-date retry headers are supported. Where the server supplies no usable header, the UI explicitly
labels a 60-second local pause as a precaution and says the server limit may last longer; it does
not invent a precise unlock time. Reset-email cooldown does not disable password sign-in. Switching
away and back does not reset the same action's pause. State is in memory only; this is user
guidance, not CAPTCHA, backend rate limiting, multi-tab protection or a guarantee of T13 success.

`node tests/r11/auth.cjs` passed three real-SDK/mocked-HTTP scenarios: returned wait, unknown wait,
and reset-only cooldown with mode switching. Tests also submit the DOM form directly to prove that
repeated handlers are guarded. Existing eight teacher and two recovery UI regressions passed. No
hosted Auth requests or emails were made by these checks.

## Optional CAPTCHA integration prepared locally

A separate public `shared/auth-captcha.js` defaults to empty, preserving current login behavior and
making no provider request. When explicitly configured with a Turnstile public site key, the teacher
page requires a fresh token for sign-in and recovery-email requests. Missing/expired/error tokens
and provider-load failure block submission. Tokens stay in memory, pass through SDK options, and are
cleared after every attempt and mode change. A verified recovery-session password change does not
require a new challenge. No CAPTCHA secret belongs in browser code or the repository.

TEST packaging accepts `--test-captcha-site-key` only for an explicit TEST teacher package. It adds
only the provider's script/frame/connect origin to those staged pages' CSP and writes only the
public configuration. The default source policy remains unchanged. Generated root paths are
rewritten for both app and CAPTCHA scripts. Production enabling requires a separately reviewed
public key/CSP change, server-side Supabase provider settings, TEST verification and owner approval;
editing just a widget or site key is insufficient. No provider account was created or settings
changed by this implementation.

Two mocked-provider/real-SDK boundary scenarios passed: token lifecycle (including expiry, one-use
