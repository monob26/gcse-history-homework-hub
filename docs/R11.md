## Findings and smallest practical approach

Four ordinary password sign-ins do not send four emails. Capacity alone is not a reason to upgrade
Supabase or buy a mail service. Keep Supabase Free and diagnose the actual limit before proposing
new values. Current docs describe separate IP buckets and project email quotas; a UI pause cannot
replace either server control. CAPTCHA reduces automation but cannot guarantee an IP bucket will
never be exhausted by hostile requests.

Incident-day live Auth logs (14 November 2026, 00:00–24:00 UTC) contain 31 HTTP 429 events with
`over_request_rate_limit`. Other grouped events include invalid-credential and successful-password
grant events. The available rate-limit records show path `/` and no grant type: they establish the
request-limit category, not the exact endpoint/bucket, configured value, blocked network identity or
duration. No email addresses, IPs, user IDs, tokens or raw log messages are recorded here.

Exact hosted Auth settings remain independently unreadable under the existing Management API
permission limitation. That denied settings endpoint was not retried. Local `supabase/config.toml`
values are not evidence of current hosted settings. No lockout was deliberately caused on live.

R8 proved one real recovery email to the owner-authorized controlled alias and a genuine password
reset. It did not establish delivery to every school teacher, three messages within an hour, or the
exact configured limits. That existing acceptance remains valid and was not rerun.

## Owner decision: retain working email configuration

The owner explicitly declined custom SMTP and any new email service. Preserve the working settings
and R8 recovery evidence. Do not change SMTP, sign up for another sender, add organization members
just for delivery, or reuse personal mailbox credentials. There is no current approval for live
settings or website changes.

For four teachers, a two-email hourly cap can be proportionate **if recovery is occasional**: normal
password sign-ins use no recovery email quota, and one or two resets in an hour fit the documented
cap. If three or all four teachers need recovery within the same hour, requests beyond the remaining
quota may need to wait for capacity. Other Auth email operations can share that quota. The sender is
best-effort, and actual recovery recipients must be authorized by the existing provider. R8 proved
delivery to its controlled alias, not to every prospective teacher address. These are known
operational constraints; department size alone does not prove that all recovery needs fit.

The existing setup is acceptable for low-volume use **subject to those documented restrictions**,
not equivalent to three guaranteed messages per hour or unrestricted delivery. Do not exhaust the
quota again merely to demonstrate the documented restriction. Retain R8's genuine recovery pass.

## Local improvements prepared

The teacher page now preserves Auth `Retry-After` through a fetch wrapper without reading/logging
payloads. It handles HTTP 429 and the documented request/email rate error codes, displays a wait,
and prevents simultaneous or repeated form submissions during that action's pause. Numeric and
HTTP-date retry headers are supported. Where the server supplies no usable header, the UI explicitly
labels a 60-second local pause as a precaution and says the server limit may last longer; it does
not invent a precise unlock time. Reset-email cooldown does not disable password sign-in. Switching
away and back does not reset the same action's pause. State is in memory only; this is user
guidance, not CAPTCHA, backend rate limiting, multi-tab protection or a guarantee of T13 success.

`node tests/r11/auth.cjs` passed three real-SDK/mocked-HTTP scenarios: returned wait, unknown wait,
and reset-only cooldown with mode switching. Tests also submit the DOM form directly to prove that
repeated handlers are guarded. Existing eight teacher and two recovery UI regressions passed. No
hosted Auth requests or emails were made by these checks.

## Optional CAPTCHA integration prepared locally

A separate public `shared/auth-captcha.js` defaults to empty, preserving current login behavior and
making no provider request. When explicitly configured with a Turnstile public site key, the teacher
page requires a fresh token for sign-in and recovery-email requests. Missing/expired/error tokens
and provider-load failure block submission. Tokens stay in memory, pass through SDK options, and are
cleared after every attempt and mode change. A verified recovery-session password change does not
require a new challenge. No CAPTCHA secret belongs in browser code or the repository.

TEST packaging accepts `--test-captcha-site-key` only for an explicit TEST teacher package. It adds
only the provider's script/frame/connect origin to those staged pages' CSP and writes only the
public configuration. The default source policy remains unchanged. Generated root paths are
rewritten for both app and CAPTCHA scripts. Production enabling requires a separately reviewed
public key/CSP change, server-side Supabase provider settings, TEST verification and owner approval;
editing just a widget or site key is insufficient. No provider account was created or settings
changed by this implementation.

Two mocked-provider/real-SDK boundary scenarios passed: token lifecycle (including expiry, one-use
reset, sign-in/reset-email forwarding, mode switches and recovery-mode controls) and provider load
failure. Three rate-limit scenarios passed. Ten staging guards cover TEST-only use, secret-like key
rejection and scoped policy generation. Eight teacher regressions, two recovery UI regressions, and
generated-package library/SRI/CSP checks passed. None establishes hosted CAPTCHA enforcement or T13
success; hosted acceptance remains pending actual provider configuration.

## Draft teacher guidance

If sign-in is limited, stop repeatedly pressing Sign in. Wait for the displayed period; if the
server did not supply a time, the suggested pause may be shorter than its limit. Ask school IT if
several teachers are affected. Repeated password-reset requests can exhaust the separate email quota
and will not fix a sign-in request limit. With the retained default sender, do not request several
reset links repeatedly: capacity is shared and delivery beyond the quota may need to wait. Do not
share teacher passwords or use unapproved networks. Final instructions must include the actual
chosen rate settings/duration once T13 is verified.
