# R11 — shared-network sign-in and recovery limits

Status on 16 November 2026: **OPEN. Investigation and local UI backoff prepared; original T13/T14
acceptance has not passed.** No hosted settings, accounts, SMTP, CAPTCHA or live pages changed. No
paid service was created. Owner estimates four teachers signing in from the school network.

## Findings and smallest practical approach

Four ordinary password sign-ins do not send four emails. Capacity alone is not a reason to upgrade
Supabase or buy a mail service. Keep Supabase Free and diagnose the actual limit before proposing
new values. Current docs describe separate IP buckets and project email quotas; a UI pause cannot
replace either server control. CAPTCHA reduces automation but cannot guarantee an IP bucket will
never be exhausted by hostile requests.

Incident-day live Auth logs (14 November 2026, 00:00–24:00 UTC) contain 31 HTTP 429 events with
`over_request_rate_limit`. Other grouped events include invalid-credential and successful-password
grant events. The available rate-limit records show path `/` and no grant type: they establish the
request-limit category, not the exact endpoint/bucket, configured value, blocked network identity or
duration. No email addresses, IPs, user IDs, tokens or raw log messages are recorded here.

Exact hosted Auth settings remain independently unreadable under the existing Management API
permission limitation. That denied settings endpoint was not retried. Local `supabase/config.toml`
values are not evidence of current hosted settings. No lockout was deliberately caused on live.

R8 proved one real recovery email to the owner-authorized controlled alias and a genuine password
reset. It did not establish delivery to every school teacher, three messages within an hour, or the
exact configured limits. That existing acceptance remains valid and was not rerun.

The built-in sender is documented as team-address-only, two messages/hour, best effort. Do not add
teachers to the Supabase organization solely to make email delivery work: that grants unnecessary
administrative access. Do not repurpose personal Gmail SMTP credentials automatically. First check
whether school IT can provide an approved existing SMTP sender; availability and authentication
policy still require confirmation. A new free transactional sender is a later option, not a reason
to create accounts or promise zero setup costs now.

## Original acceptance criteria retained

Recovered the original `ADVERSARIAL.md` from repository branch `review/r4-pupil-timers`:

- T13: deliberately reach a sign-in rate limit on one network; try another teacher correctly;
  identify the limit/duration; pass when its owner knows and deliberately configures it for the
  school and teachers have written instructions. Any future exercise must be bounded and separately
  authorized on TEST, using fictional accounts; do not hammer live.
- T14: three real test-teacher password-reset requests within an hour, plus an unknown address;
  every real request must produce received email and known/unknown response behavior must match.
  Respect the per-user interval too. A 200 for an unknown address, admin-generated link, local mail
  emulator or mocked delivery is not a substitute for receipt.

The unmodified criteria cannot be marked passed with the current default sender. If the owner
chooses to accept its lower quota, that is an explicit revision/deferral of T14 and CAPTCHA scope,
not completion of the original R11. No such revision is assumed.

## Local improvements prepared

The teacher page now preserves Auth `Retry-After` through a fetch wrapper without reading/logging
payloads. It handles HTTP 429 and the documented request/email rate error codes, displays a wait,
and prevents simultaneous or repeated form submissions during that action's pause. Numeric and
HTTP-date retry headers are supported. Where the server supplies no usable header, the UI explicitly
labels a 60-second local pause as a precaution and says the server limit may last longer; it does
not invent a precise unlock time. Reset-email cooldown does not disable password sign-in. Switching
away and back does not reset the same action's pause. State is in memory only; this is user
guidance, not CAPTCHA, backend rate limiting, multi-tab protection or a guarantee of T13 success.

`node tests/r11/auth.cjs` passed three real-SDK/mocked-HTTP scenarios: returned wait, unknown wait,
and reset-only cooldown with mode switching. Tests also submit the DOM form directly to prove that
repeated handlers are guarded. Existing eight teacher and two recovery UI regressions passed. No
hosted Auth requests or emails were made by these checks.

## Draft teacher guidance

If sign-in is limited, stop repeatedly pressing Sign in. Wait for the displayed period; if the
server did not supply a time, the suggested pause may be shorter than its limit. Ask school IT if
several teachers are affected. Repeated password-reset requests can exhaust a separate email quota
and will not fix a sign-in request limit. Do not share teacher passwords or move school data onto an
unapproved personal network. Final instructions must include the actual chosen settings/duration
once T13 is verified.
