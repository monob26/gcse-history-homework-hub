## Prepared branch protection

`r8/main-protection.proposed.json` is an unapplied request body for `main` on both repositories. It
requires PRs and resolved conversations, applies to administrators, blocks force-pushes and
deletion, and dismisses stale reviews. Zero required approving reviews allows a solo owner to merge
their own PR; it does not require a second person. No status checks are invented: workflow
automation belongs to R9. The owner should confirm whether a second reviewer is available before
increasing the review count.

Applying protection needs an authorized GitHub connection with repository Administration write
permission, or the owner can apply these settings in each repository's Settings → Branches. Confirm
via the branch/protection endpoints after application. No attempt to bypass the current integration
restriction was made.

## Prepared isolated test configuration

The existing default static-copy command remains byte-compatible. Test staging is explicit and
requires a real, different Supabase project and a different teacher URL:

```sh
python3 scripts/prepare-pages.py pupil work/test-pupil \
  --environment test --test-config work/test-config.json
python3 scripts/prepare-pages.py teacher work/test-teacher \
  --environment test --test-config work/test-config.json
```

Start with `r8/test-config.example.json` and replace its placeholders with the test project URL, its
public publishable key and the approved test teacher URL. The example intentionally fails validation
until configured. Never supply a server/secret key. The tool rejects the current project's URL/key,
the current teacher redirect, malformed project URLs, credential-bearing URLs and unexpected config
fields before writing output. It writes the override only into the staging copy of
`shared/config.js`; tracked source configuration is unchanged. Deploy both test artifacts to
separately approved test-site URLs. Do not copy test configuration into the existing live Pages
roots.

The test project's URL/key association must be checked with that project's own API before
publication; syntactic validation alone cannot prove that a key belongs to it. After publication,
inspect the public test config and browser requests to prove they reach only the test project, then
use fictional data for acceptance. Live pages should still reference their current project.
